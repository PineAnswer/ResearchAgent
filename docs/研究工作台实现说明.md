# 综述研究工作台实现说明

## 1. 功能边界

研究工作台是最终综述旁侧的二次研究界面。只要项目快照中存在 `NarrativeReview`，前端 `renderOutcome()` 就会在综述正文旁创建工作台；项目处于写作恢复状态时，只要已有该产物也可以继续使用。

工作台提供四类能力：

- 围绕综述、当前选段和项目入选论文进行多轮流式聊天；
- 将综述选段连同评论保存为批注；
- 保存不依附选段的普通笔记；
- 保存一组问答，并通过会话置顶状态收藏当前研究。

它复用项目、会话、个人文献库和用户会话，不创建新的研究项目，也不推进研究状态机。

## 2. 页面装配与浏览器状态

### 2.1 装配条件

页面加载项目时，前端从项目快照中读取最新 `NarrativeReview`：

```text
GET /api/projects/{project_id}
  → get_project()
  → sync_project(project_id)
  → get_snapshot(project_id)
  → renderOutcome(snapshot)
  → renderNarrativeReviewHTML(narrative)
  → renderResearchWorkspace(narrative, reviewElement)
```

没有 `NarrativeReview` 时，`renderOutcome()` 显示研究进度、证据不足或恢复入口，不挂载研究工作台。

### 2.2 临时状态与持久状态

浏览器中的工作台状态分为两类：

| 状态 | 保存位置 | 切换项目或刷新后的结果 |
| --- | --- | --- |
| `researchSelection` | 浏览器内存 | 清空 |
| `researchChatHistory` | 浏览器内存 | 清空 |
| `researchWorkspaceTab` | 浏览器内存 | 当前页面会话内保留 |
| `researchWorkspaceWidth` | 浏览器内存 | 当前页面会话内保留，刷新回到 430 px |
| `researchNotes` | SQLite 的 `research_notes` | 重新请求并恢复 |
| 收藏状态 | SQLite 的 `conversations.pinned_at` | 随项目快照和会话列表恢复 |

因此，多轮聊天本身只在当前浏览器页面中连续存在。用户点击“保存这组问答”后，该问答才进入长期存储。

### 2.3 布局与宽度调整

宽屏下工作台固定在浏览器右侧，默认宽度为 430 px。`createResearchWorkspaceResizer()` 提供以下调整方式：

- 指针拖动改变宽度；
- 键盘左右方向键每次调整 24 px；
- 双击恢复到 430 px；
- 最小宽度为 380 px，最大宽度由当前项目视图宽度动态计算。

当视口宽度不超过 1100 px 时，CSS 隐藏拖动条，将工作台移动到综述正文下方，并使用可用宽度。

## 3. 综述选段工作流

选段由综述正文元素上的 `mouseup` 事件捕获：

```text
用户在 NarrativeReview 中划选文字
  → window.getSelection()
  → trim()
  → 截断到前 12,000 字
  → state.researchSelection
  → 更新聊天上下文卡片和批注表单
```

只有选区锚点位于当前综述元素内部时才会接收该选段。选段被同时用于：

- 下一次聊天请求的 `selected_text`；
- 新建 `annotation` 时的 `selected_text`；
- 保存 `qa` 时的选段快照。

用户可以通过上下文卡片的关闭按钮清除选段。清除后，聊天继续围绕项目上下文进行，笔记按钮恢复为“保存笔记”。

## 4. 多轮流式聊天

### 4.1 浏览器请求

当前工作台固定调用：

```http
POST /api/projects/{project_id}/assistant/stream
Content-Type: application/json
```

请求体为：

```json
{
  "scope": "project",
  "question": "用户本轮问题",
  "selected_text": "当前选中的综述文字，可为空",
  "history": [
    {"role": "user", "content": "上一轮问题"},
    {"role": "assistant", "content": "上一轮回答"}
  ]
}
```

`ProjectAssistantRequest` 在进入路由前执行请求体校验：

| 字段 | 约束 |
| --- | --- |
| `scope` | `selection`、`narrative`、`project`、`library` 之一；工作台发送 `project` |
| `question` | 1～4,000 字 |
| `selected_text` | 最多 12,000 字 |
| `history` | 最多 40 条 |
| 单条历史消息 | `user` 或 `assistant`，1～30,000 字 |

发送前，前端排除标记为 `failed` 的回答，并截取最近 40 条有效消息。本轮用户消息与待填充的助手消息随后才加入页面状态，避免在请求历史中重复本轮问题。

### 4.2 服务端上下文组装

`ResearchSupervisor.stream_project_chat()` 按下面的顺序构造上下文：

1. 通过仓储读取项目，验证项目存在且属于当前用户；
2. 读取该项目所有产物，选取最新 `NarrativeReview`；
3. 如果 `selected_text` 非空，先加入“用户选中的综述原文”；
4. 将综述标题、摘要、章节正文和小节正文拼成“当前综述”；
5. 调用 `sync_project(project_id)`，提取关系状态为 `included` 的项目论文；
6. 调用 `retrieve_library_sources(..., library_ids=included_ids, limit=16)`，加入与问题相关的本地文献片段；
7. 按上述顺序将总上下文截断到 120,000 字；
8. 在系统消息后附加最近 40 条历史消息和本轮问题，调用聊天模型的 `astream()`。

当前工作台的 `scope="project"` 会把检索范围限制在项目入选论文。底层方法也支持 `library`，该模式会在当前用户的完整文献库中检索；当前工作台界面没有暴露这个切换项。

系统提示允许模型使用自身知识，并明确研究上下文只作为辅助材料。因此这条链路适合解释、追问和发散讨论，不承诺每个结论都带结构化文献引用。

### 4.3 SSE 传输协议

API 将模型输出封装为 Server-Sent Events：

```text
event: delta
data: {"text":"新生成的文本片段"}

event: done
data: {}

event: error
data: {"message":"错误原因"}
```

路由返回以下响应头：

- `Content-Type: text/event-stream`；
- `Cache-Control: no-cache`；
- `X-Accel-Buffering: no`，避免反向代理聚合流式片段。

请求体未通过 Pydantic 校验时，FastAPI 在建立 SSE 流之前返回 HTTP 422。流建立后的项目读取、上下文检索或模型异常会转换为 `error` 事件。

### 4.4 浏览器消费与 Markdown 安全

浏览器使用 `ReadableStream.getReader()` 读取字节流，以空行切分 SSE 事件块：

- `delta` 追加到当前助手消息并立即重新渲染 Markdown；
- `error` 保存错误信息，流结束后将本轮回答标为失败；
- 成功结束后仅保留最近 40 条聊天消息，并显示“保存这组问答”按钮。

Markdown 由本地 `marked` 解析器处理。前端禁用原始 HTML token，再通过允许标签集合重建 DOM；链接只接受 `http:`、`https:` 和 `mailto:`，外站链接附加 `noopener noreferrer`。解析器不可用时降级为纯文本段落。

流式聊天没有摘录兜底。模型没有返回文本、SSE 返回错误或网络中断时，页面直接显示失败原因；该失败回答不会进入下一轮历史。

## 5. 同步范围问答接口

系统另有同步接口：

```http
POST /api/projects/{project_id}/assistant
```

它调用 `answer_project_question()`，适合需要确定范围、结构化引用和模型失败兜底的调用方。当前研究工作台使用流式接口，没有调用这条同步链路。

同步问答支持四种范围：

| 范围 | 主要材料 |
| --- | --- |
| `selection` | 用户选段，并从项目入选论文检索相关片段 |
| `narrative` | 综述摘要、章节和小节 |
| `project` | 综述及项目入选论文 |
| `library` | 当前用户的完整文献库 |

同步链路分成两种执行方式：

- `selection`、`narrative` 和 `project`：把范围内材料整理成带 `source_id` 的有界上下文，使用 `LibraryAgentResponse` 结构化输出。回答中的 `[[source_id]]` 和 `cited_source_ids` 会合并校验，有效来源转换成 `[1]` 编号并返回引用元数据；未知标记、模型异常或空回答会退回当前范围内最多四条原始摘录。模型可以在没有引用的情况下解释通用概念，但不能给不存在的来源附标记。
- `library`：调用独立的 `library-research-agent`。服务先把最多 500 篇论文的目录摘要注入 system prompt，再允许 Agent 串行调用 `search_library`、`retrieve_library_passages` 和 `get_library_paper_context`，模型调用总上限为 20。该路径读取最后一条非空 AI 文本，从 HTML 注释 `<!-- coverage: ... -->` 提取覆盖说明，再把工具真实注册的 `[[source_id]]` 转换为编号引用。图不可用、Agent 异常或空回答时，退回最多八条本地关键词检索摘录。

`selection`、`narrative` 和 `project` 要求项目已有 `NarrativeReview`，`selection` 还要求非空选段；`library` 直接进入当前用户的全库问答链路。全库自由文本路径当前会跳过未在工具来源注册表中找到的标记，未识别的 `[[...]]` 可能留在回答正文中，这是与结构化项目问答不同的已知边界。

## 6. 批注、笔记与已保存问答

### 6.1 数据模型

三种记录共用 `ResearchNote`：

| `kind` | 关键字段 | 用途 |
| --- | --- | --- |
| `note` | `content` | 独立研究笔记 |
| `annotation` | `selected_text`、`content` | 综述原文批注 |
| `qa` | `question`、`answer`、`selected_text`、`citations` | 人工保存的一组问答 |

流式聊天只返回纯文本片段，所以当前工作台保存 `qa` 时写入空的 `citations` 列表。同步范围问答接口可以返回结构化引用，其他调用方可将其一并保存。

### 6.2 API 与校验

```text
GET    /api/projects/{project_id}/notes
POST   /api/projects/{project_id}/notes
PATCH  /api/projects/{project_id}/notes/{note_id}
DELETE /api/projects/{project_id}/notes/{note_id}
```

创建记录时，API 还执行以下业务校验：

- `note` 和 `annotation` 必须有非空 `content`；
- `annotation` 必须有非空 `selected_text`；
- `qa` 必须同时有非空 `question` 和 `answer`。

字段长度上限为：选段 12,000 字、正文 20,000 字、问题 4,000 字、回答 30,000 字、引用列表 100 项。

前端目前提供新建和删除操作。后端同时支持 `PATCH` 更新：它先核对记录属于 URL 中的项目，再保留原始 `created_at`、刷新 `updated_at` 并通过仓储覆盖保存。

### 6.3 SQLite 写入与恢复

保存链路为：

```text
工作台表单
  → POST /notes
  → ResearchNote(note_id="rnote-...")
  → repository.save_research_note()
  → 校验项目归属
  → INSERT ... ON CONFLICT DO UPDATE
  → research_notes
```

`research_notes` 保存 `note_id`、`project_id`、`kind`、完整 `payload_json`、`updated_at` 和 `user_id`。读取时按 `updated_at DESC` 返回，因此最新保存或更新的记录排在最前。

重新打开含综述的项目时，`renderOutcome()` 先挂载工作台，随后异步调用 `GET /notes`。请求返回前可以先显示空列表；返回后只有项目 ID 仍与当前页面一致时才写入浏览器状态，避免快速切换项目造成跨项目显示。

## 7. 收藏研究

“收藏研究”复用会话的置顶字段：

```text
点击收藏
  → PATCH /api/conversations/{conversation_id}
  → {"pinned": true/false}
  → update_conversation()
  → 设置或清空 conversations.pinned_at
  → 重新加载左侧会话列表
```

收藏后，会话列表按“已置顶、置顶时间、更新时间”排序。取消收藏只清空 `pinned_at`，不会删除项目、产物、聊天保存项或研究笔记。归档会话时仓储会同时取消置顶。

只有关联 `ResearchConversation` 的项目可以收藏。直接通过兼容 API 或 CLI 创建且没有会话记录的项目，工作台会提示“该研究缺少可收藏的会话记录”。

## 8. 用户隔离与删除生命周期

每个 HTTP 请求先经过 `isolate_user_session` 中间件：

1. 读取 `research_agent_session` HttpOnly Cookie；
2. `resolve_user_session()` 解析用户；
3. 在 `repository.user_scope(user_id)` 中执行路由；
4. 新会话写回有效期一年的 `SameSite=Lax` Cookie。

默认 `RESEARCH_AGENT_MULTI_USER_MODE=false` 时，本地浏览器会话映射到共享本地用户。启用多用户模式后，新浏览器会话创建独立用户。项目读取、笔记 CRUD、会话置顶和文献检索都使用当前 `user_id` 过滤。

永久删除项目时：

- 仓储先确认项目属于当前用户；
- 删除状态事件、产物、项目论文关系和搜索审核选择；
- 删除 `projects` 行后，SQLite 外键级联删除会话、运行记录、会话消息、研究笔记和研究关系；
- `ArtifactExporter` 删除该项目的导出目录。

单独删除研究笔记只移除当前用户拥有的指定 `note_id`。

## 10. 当前工作流总结

研究工作台的主链路可以概括为：

```text
项目快照中的 NarrativeReview
  → 挂载综述正文与工作台
  → 可选：捕获综述选段
  → 组装当前综述 + 入选论文片段 + 最近对话
  → 模型流式生成
  → 浏览器安全渲染 Markdown
  → 可选：将问答、批注或笔记写入 SQLite
  → 再次打开项目时恢复持久记录和收藏状态
```

聊天上下文负责当前页面内的连续追问；`research_notes` 负责跨页面和跨进程保存人工选择的研究记录；会话 `pinned_at` 负责收藏和列表排序。三者生命周期独立。
